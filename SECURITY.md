# Security Policy

Geminarr reads someone's private conversations through **the signed-in session of a Google account**, which is held by a browser container of its own (a browser profile), not by Geminarr. We take security reports seriously.

## Reporting a vulnerability

**Do not open a public issue.** Use GitHub's [private vulnerability reporting](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability) on this repository ("Security" tab, then "Report a vulnerability").

Please include the affected version, reproduction steps and the impact you observed. We aim to acknowledge reports within 7 days.

## Supported versions

Until 1.0, only the latest release receives security fixes.

## Security model (summary)

The full model, with the threats and their controls, is [SPEC §11](docs/SPEC.md#11-security-and-privacy); the decisions are [ADR 0004](docs/adr/0004-a-dedicated-google-account-never-the-main-one.md) and [ADR 0008](docs/adr/0008-the-agent-merges-technical-pull-requests.md).

**The one rule that matters to you as an operator: sign Geminarr in to a dedicated Google account, never to your main one.** A Google session is valid across all the services of an account, mailbox included, and a copy of it bypasses 2-step verification. A leak of this container must reach nothing but Gemini conversations.

**True today** (foundation, operator access, the link to Mnemarr)

- **Closed by default** ([ADR 0011](docs/adr/0011-one-operator-a-session-in-memory-and-everything-closed-but-the-probes.md)). Anonymous are the probes (`/health/live`, `/health/ready`), the static shell of the interface and the sign-in call. **Every other call, the API description included, needs a session; an unknown API path is a 401 too.** A fallback policy requires it everywhere, so an endpoint nobody thought about is closed.
- **One operator**: a name and a password in a mounted file (at least `GEMINARR__AUTH__MINPASSWORDLENGTH` characters, twelve by default, read at each sign-in; a sandbox without a browser may lower it; with a browser the container refuses to start below twelve, ADR 0018). Without them nobody can sign in: the container stays alive and closed. The comparison takes the same time whatever is wrong, a wrong name and a wrong password are told the same, and **five wrong passwords lock a name for fifteen minutes** (counted per name whether it exists or not, in memory).
- **The session** is a cookie (`HttpOnly`, `SameSite=Strict`, `Secure` and `__Host-` prefixed unless a sandbox says otherwise, no expiry date) backed by a session **in memory** with an absolute lifetime (12 hours by default). Signing out removes it on the server, so a copied cookie is dead at once; a restart ends every session (the keys are in memory too).
- **A write needs the `X-Geminarr-Request` header**, checked by the server before the sign-in (a cross-site form or link cannot send it), on top of `SameSite=Strict`.
- **A request for a `Host` that is not allowed is refused** (DNS rebinding), the probes excepted (a platform calls them by the address of the pod): `GEMINARR__ALLOWEDHOSTNAMES` and the host of `GEMINARR__PUBLICURL`.
- The page *Settings* never shows a secret, nor the path of its file, nor the name of the operator; the health says what is wrong with a stable code and never a path or an exception.
- Every response, errors included, carries conservative security headers (nosniff, no framing, no referrer, a Content-Security-Policy that lets everything come from the application only); the API and its description are never cached; an unknown path under `/api` is never the HTML shell; an error never shows its cause; a body larger than a sign-in can be is a 413.
- The image runs as a non-root user with no shell; the deployment examples run it with a read-only root file system, no capability, no service-account token and an ingress-only network policy.
- The CI scans for secrets and vulnerable dependencies, and the code is analysed by CodeQL and SonarQube; Dependabot waits a week before taking a new version.
- **The Mnemarr key** (vertical 2) is ingest-only and bound to the machine, and is **a file** (mode `0600`, written by a move over the old one) that is never in the database, a log, an answer of the API or the page; it goes only to the address that was configured, over HTTPS (a loopback address or an explicit sandbox switch excepted), redirects are not followed, every call is bounded, and a failure says what kind it was and never what was sent or where. Unlinking forgets it.
- **What waits for Mnemarr** is the only text of a conversation that Geminarr ever holds, in a database file that only its owner reads, until Mnemarr acknowledges it; the database has no column for a turn, and **no log line holds a title or a turn** (counts, codes and durations only).
- **The session is made by a person, by hand, in a browser container of its own** (vertical 3, [ADR 0016](docs/adr/0016-the-browser-is-a-container-of-its-own.md)): an ordinary Chromium with a web desktop, that the account provider accepts because nobody drives it at sign-in. **Geminarr never types a credential, never launches a browser, and never tries to hide that a program drives a browser**: it only attaches to the browser, through its debugging address, opens a page of its own on the assistant's address, looks at where it ends (the assistant's page, or a sign-in page: the session is gone), closes it, and lets go. *Disconnect* clears the cookies of the browser. The debugging address is **the key to the session**: it listens on the loopback of the network namespace that the two containers share, and is in no Service, no published port and no network policy.
- It still **reads nothing real** (a demonstration reader with invented conversations is a setting for a sandbox): the conversations come with the next vertical, behind this access. Geminarr itself holds **no Google session**: the browser container does.

**The rest of the model** (the browser container, the relay and the session are built with the vertical of the connection; the masking of secrets and the reading of Takeout come with the reader)

- **The browser container is a third party's image, pinned by digest**, started as root by its own init (it sets the user from `PUID` and `PGID`) and running Chromium as that user. It is a bigger surface than Geminarr's own chiseled image, so it is isolated by what surrounds it: its own volume, no published port, no Service and no sign-in of its own (it is reachable by Geminarr alone, ADR 0017), a network policy, memory limits, and the dedicated account (whose damage is bounded). Harden it further for your platform, and test that Chromium still starts. The choice of the image is the maintainer's.
- **The session** lives in the **browser container's volume** (its profile): a volume of its own, never in logs, an API response, a health page, a crash dump or a backup in the clear; nobody else may read it, and the screen of the browser is as sensitive as the account (whoever opens it uses the account): Geminarr relays it behind the operator's sign-in only (the browser has no address and no login of its own), so **the operator's password is the key to the session**, and the relay is read as such (origin of the WebSocket, no cookie in either direction). **The desktop is another program's, so it is served on an origin of its own** (a second port, opened by a single-use ticket of the operator's session, [ADR 0019](docs/adr/0019-the-desktop-has-an-origin-of-its-own-opened-by-a-ticket.md)): its scripts never run where the operator's cookie is sent, and its own cookie is worth nothing on the page's origin.
- **Geminarr's own process reaches Mnemarr and nothing else, whatever the pod's network policy allows the browser** ([ADR 0020](docs/adr/0020-geminarrs-own-egress-is-limited-by-its-user-in-the-shared-namespace.md)): in the namespace that the two containers share, rules of the output chain name Geminarr's process by its user and refuse every other destination; a container of their own sets them once, with `NET_ADMIN` and nothing else, and Geminarr has no capability to change them. A flaw in Geminarr (it parses hostile text) cannot send what it holds to a host that the browser may reach.
- **Read-only, on the assistant's own pages.** Geminarr navigates to the assistant's host only (the one other page it opens, on the operator's click on *Sign in*, is the account provider's sign-in page, `GEMINARR__BROWSER__SIGNINURL`, in a tab of the browser: opened over the debugging port's plain HTTP, nothing attached), and never types, clicks or submits anywhere: it opens a page of its own to look at where the assistant's address ends. The driver sees every tab for the seconds of a pass, so a pass first reads the list of tabs (plain HTTP, nothing attached) and steps aside while one is on a sign-in page. What Chromium itself reaches is the network policy of the pod's ([network.md](docs/network.md)).
- **Secrets are masked before anything leaves the container**, and again by Mnemarr (with the reader that reads something real, vertical 4).
- **A Takeout archive is hostile input**: read without extracting by name, with bounds on entries and sizes.
- **Geminarr sends no mail** and holds no mail credential: it signals Mnemarr, which writes to the operator from its own mailbox, pointing to Mnemarr's own page and never repeating anything Geminarr wrote ([ADR 0012](docs/adr/0012-the-attention-mail-points-to-mnemarr-not-to-the-satellite.md)).
