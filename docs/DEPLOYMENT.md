# Deploying Geminarr as code

> What a deployment of Geminarr looks like, so that the maintainer's private infrastructure repository can describe it without anything being rediscovered. **This repository holds no real value**: the generic examples are in [`deploy/`](../deploy/README.md); the real folder lives in the private GitOps repository.

## The three levels

See [ADR 0007](adr/0007-geminarr-is-described-as-code-at-three-levels.md): the repository (Terraform, `github-template/repos/geminarr.yaml`), the image (this repository's pipeline), the deployment (`apps/geminarr/` of the GitOps repository, applied by Flux).

## Shape of the GitOps folder (`apps/geminarr/`)

Same as the other applications of the cluster:

| File                             | Content                                                                                                                                                                                                                                                         | Geminarr-specific                                                                                                                                                                                               |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `namespace.yaml`                 | The namespace `geminarr`                                                                                                                                                                                                                                        | —                                                                                                                                                                                                               |
| `secret-extension.enc.yaml`      | The token of the extension (32 characters or more, random), mounted as a file: `GEMINARR__EXTENSION__TOKENFILE`, **and the same token in the browser's policy**                                                                                                 | SOPS-encrypted. Rotating it is two changes (this and the policy), one after the other                                                                                                                           |
| `secret-browser-policy.enc.yaml` | The policy of the browser container, mounted in `/etc/chromium/policies/managed/` of the browser container: it installs the extension, gives it the address of Geminarr (the loopback of the pod) and its token, and keeps the browser to the assistant's pages | Made by your tooling from [deploy/browser/policy.example.json](../deploy/browser/policy.example.json) (the id of the extension is in the update manifest of Geminarr); SOPS-encrypted, since it holds the token |
| `pvc.yaml` | `geminarr-data` (database, outbox, Mnemarr key; ~2 Gi) **and `geminarr-browser`** (the configuration of the browser container, **its profile included: the signed-in session**; ~1 Gi) | Two claims on **local** storage with a retaining class, on the same node as the pod. **The browser claim is never backed up in the clear**: it is the session of a Google account |
| `secret-mnemarr.enc.yaml` (optional) | The key that Mnemarr gave to this machine, or a one-time code, mounted as a file: `GEMINARR__MNEMARR__KEYFILE` or `GEMINARR__MNEMARR__ENROLMENTCODEFILE` | SOPS-encrypted. The key is ingest-only and bound to the machine. Without either, the operator pairs on the page _Mnemarr_ (the key is then written in the data folder) |
| `identity/` (optional) | The picture of the menu (a png, webp or svg), mounted as a file: `GEMINARR__IDENTITY__LOGOFILE`, with `GEMINARR__IDENTITY__NAME` | The same files as Portarr's and Mnemarr's GitOps folders hold; the picture is personal and never goes in this repository |
| `secret-operator.enc.yaml` | The operator's password (SOPS-encrypted), mounted as a file: `GEMINARR__AUTH__ADMINPASSWORDFILE` | The operator's name is a plain setting; choose one that is not obvious. Rotating the secret needs no restart |
| `deployment.yaml` | **One pod, two containers and the egress guard's two init containers** (ADR 0016, 0020): Geminarr (non-root uid 1654, read-only root, no capabilities) and **the browser container** (an ordinary Chromium with a web desktop; a third party's image **pinned by digest**, never `latest`: the choice of the image is the maintainer's, SPEC Q-18). One replica, `Recreate`, no service-account token, `emptyDir` for `/tmp` and for the browser's shared memory (`/dev/shm`, 1 Gi, in memory), probes on `/health/*`, the Geminarr image line marked for the image policy. The two containers share the pod's network, so the browser's web desktop (`127.0.0.1:3000`) is never on a network | The browser container starts as root (its init sets the user): test that Chromium starts on your platform before hardening it. Limits: Geminarr 256 Mi; the browser 2 Gi |
| `configmap-egress.yaml` (in the example: `geminarr-egress`) | The rules of the egress guard, `rules.v4` and `rules.v6` (the files of `deploy/egress/`), loaded by two init containers of the pod | **Geminarr's own process reaches Mnemarr and nothing else** (ADR 0020): it is named by its user (1654) in the namespace that the browser shares, whatever the network policy allows the browser. Write Mnemarr's address, port and the name servers; a change of Mnemarr's address is a change here and a restart. The init containers need `NET_ADMIN` and nothing else: the namespace must allow it (Pod Security `privileged`, or an exemption for them) |
| `configmap-browser-init.yaml` | The init script of the browser container, `loopback-only.sh` (the file of `deploy/browser/`), mounted in `/custom-cont-init.d/` with mode `0755` | It makes the browser's web desktop listen on the loopback of the pod only (the image listens on every interface) and refuse any request that names another origin than Geminarr's: without it, another pod, or a page that the browser itself loads, could open a desktop that has no sign-in. Test it again for any other image or version (`ss -ltn` in the container: nothing off the loopback but Geminarr's own ports, 8282 and 8283; Geminarr checks it too and closes the desktop's origin otherwise) |
| `service.yaml` | One `ClusterIP`: Geminarr on 8282 and the desktop's own origin on 8283 (ADR 0019), Geminarr alone. The browser's desktop (3000) is in none of them | — |
| `ingress.yaml` | **Geminarr's page, and the desktop's own origin** (a second host, or a second port, of the same proxy; its address is `GEMINARR__BROWSER__DESKTOPPUBLICURL`), with the login of your reverse proxy in front of the page if you have one (HTTPS: the browser's desktop needs a secure context) | Not anonymous; WebSocket upgrades pass (the relayed desktop uses one). The desktop's origin is closed without the cookie that a ticket of the operator's session gives, so it needs no login of the proxy (a second login would only get in the way of the window that the page opens). The browser container has no ingress and no login of its own |
| `networkpolicy.yaml` | Ingress: the proxy only, on 8282 and 8283 (nothing lets in 3000). Egress: DNS and the Mnemarr address for Geminarr; https to the assistant and to the account provider's sign-in for the browser container (a policy knows addresses, not names: Cilium `toFQDNs`, or port 443 for this pod only) | The list is the one in [network.md](network.md); a change is a decision. **No policy may open the browser's desktop port** |
| `image-automation.yaml` | `ImageRepository`, `ImagePolicy` (`>=0.1.0`), `ImageUpdateAutomation` limited to this folder | Same as the other applications |
| `kustomization.yaml` | Lists the files; a `configMapGenerator` only if a config file appears | — |

The settings are the environment variables of [configuration.md](configuration.md); secrets are mounted files (`…FILE`).

## The extension and the browser

The reader is an extension in a browser that a person signed in to ([ADR 0022](adr/0022-the-reader-is-an-extension-in-the-browser-a-person-signed-in-to.md)). To describe it as code:

1. **The signing key** (once, by the maintainer): an RSA 2048 key in PKCS#8 PEM (`openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048`), stored as the repository secret `EXTENSION_SIGNING_KEY` (in `github-template`, `repos/geminarr.yaml`) and in the maintainer's own vault. **Losing it, or changing it, makes a new extension**: the browsers of the deployments would have to be pointed at the new id. The release pipeline refuses to publish without it.
2. **The id of the extension**: read it from the first release's package (`extension.json` in the image, or `GET /api/v1/extension/update.xml`, the `appid`). It is the same for every release signed by the same key.
3. **The token**: random, 32 characters or more, one secret. In Geminarr it is the file of `GEMINARR__EXTENSION__TOKENFILE`; in the browser it is the `token` of the policy.
4. **The browser's policy** (`/etc/chromium/policies/managed/geminarr.json`), built from [`deploy/browser/policy.example.json`](../deploy/browser/policy.example.json): the id, the `update_url` (`<address of Geminarr as the browser reaches it>/api/v1/extension/update.xml`), `geminarrUrl`, the token. A Secret, since it holds the token. **The rest of the file is what keeps the promises of SECURITY.md in the browser itself**: no other extension (`ExtensionSettings` `*` blocked), no developer tools and no debugging port, no password manager, no sync, and the pages it may open are the assistant's (`URLBlocklist` `*`, `URLAllowlist`; adapt it to the hosts your page needs, the list is the one of [network.md](network.md)). A browser whose policy is not loaded is not hardened: check `chrome://policy`.
5. **The names**: the name that the browser reaches Geminarr by is in `GEMINARR__ALLOWEDHOSTNAMES`; if it is not the name of the request that the update manifest should carry (a proxy that ends TLS), set `GEMINARR__EXTENSION__PUBLICURL`.
6. **The browser's own sandbox**: the pinned image that the e2e stack and the sandbox use starts Chromium with `--no-sandbox` (a choice of the image: it needs no user namespace). Geminarr cannot change that; what stands in for it is the container's own hardening in the examples (no capability beyond the few the image needs, the runtime's default seccomp profile, no incoming connection, an egress list, the browser's policy) and the fact that the browser reads one origin. An image whose sandbox is on (`chrome://sandbox`) is better; it needs user namespaces or its own seccomp profile (SPEC Q-10).
7. **Updating the extension**: a release of Geminarr carries the new package; the browser takes it within hours (its own update check is about every five hours, and the extension asks every hour). To force it at once, remove the entry of the policy, restart the browser, put it back.

## Order of a first deployment (vertical 7)

1. The release `0.1.0` exists and its image is public (or the pull secret is in the folder).
2. The folder is added to the GitOps repository; Flux applies it; the pod starts; `/health/ready` is green; the browser container is up; the state is `not-connected` (or asks to sign in).
3. The operator opens Geminarr's page (the proxy's single sign-on if there is one, then its own login), pairs it with Mnemarr (or the key/code was provided), then presses **Sign in** on the page _Connection_, which opens the browser's desktop in a window (its own origin, opened by a ticket of the session: no second login), and **signs in by hand to the dedicated account**. The next pass finds the session: `connected`.
4. Mnemarr shows the machine `gemini` online; the first pass sends the recent conversations; the backfill walks the rest slowly.
5. Portarr registers the application and checks its health endpoint.

## Test instances

A test or demo instance runs on the **build machine**, not on the production cluster, at an address the maintainer can open, **with a login** (a service that listens on the network protects itself). Its browser container's volume is that of a spike: it is deleted when the spike's result is written down.
