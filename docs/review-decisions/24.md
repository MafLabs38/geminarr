# Review decisions: pull request #24

> The browser is a container of its own, and Geminarr attaches to it (vertical 3, ADR 0016). Round 1 read head `b265b3d`; the answers below are on the head that follows it.

## R-24-1 | architecture | major | fixed

- **Finding**: `not-connected` cannot last once a browser is configured: a browser nobody signed in to reports signed-out, and the state turns `needs-login` after the passes.
- **Where**: `ConnectionTracker`, `WebReader`, SPEC §7.
- **Reason**: the behaviour is the intended one (a configured browser without a session *is* "sign in"); what was wrong was the wording. SPEC, the runbook and the reason texts now say when each of `not-connected` (no browser configured, or just disconnected) and `needs-login` (a browser, nobody signed in) is shown.

## R-24-2 | architecture | major | fixed

- **Finding**: the pod-wide egress rule (any public address, port 443, minus the private ranges) also applies to Geminarr's own process, as a network policy cannot tell the two containers apart.
- **Where**: `deploy/kubernetes/geminarr.example.yaml`, `docs/network.md`, ADR 0016 ("price of the shared namespace").
- **Reason**: fixed as it is worded (the maintainer refused the cost): ADR 0020 / D-28. In the namespace that Geminarr shares with the browser, rules that name Geminarr's own process by its user (uid 1654) let it reach Mnemarr's address and port, the browser's two loopback ports and the listed name servers, and refuse the rest, whatever the pod's network policy allows the browser. A one-shot container with `NET_ADMIN` sets them before Geminarr starts and Geminarr cannot change them; Geminarr checks, from time to time, that a connection to an address on no list is refused at once and closes the desktop and the reading while it is not. Proven on a real namespace by the end-to-end stack (two probes, one as each user), by the sandbox, and by tests that the example files agree. **What it leaves** (a Geminarr that runs an attacker's code can still ask the browser, over the debugging port, to go where the browser may) is the browser's reach, measured and written in ADR 0020: it is R-24-34.

# Round 3 (head `81b9a09`)

## R-24-33 | architecture | major | fixed

- **Finding**: the attachment is not passive: Playwright shows every tab of the browser to the driver, and a pass every twenty minutes could land in the middle of a person's sign-in (the pattern the provider refused in Q-14). The documents claimed "never touches a page it did not open".
- **Where**: `CdpBrowserHost`, `PassRunner`, SECURITY.md, SPEC §7.3.
- **Reason**: a pass now first reads the list of tabs that the debugging port serves over plain HTTP (nothing attached); when one is on a sign-in page, it steps aside (`SessionCheck.SigningIn`, the run is skipped with `signing-in`, the connection says nothing) and the next pass looks again. Tested in Core (the state is unchanged, nothing is sent) and end to end against a real Chromium container: with a tab on a sign-in page the assistant is not asked for its page; once it is closed, it is. The documents now say what is true (the driver sees the tabs for the seconds of a pass), and what the provider does with that on a real account stays Q-17. Raw CDP without Playwright is a larger change that Q-17's result may or may not justify; it is not decided here.

## R-24-34 | architecture | major | declined

- **Finding**: R-24-2 is still open (and D-08 is held only by an FQDN-aware policy where one exists): what Chromium may reach is the network policy of the deployment, and no route filter in the product holds it. Raised again with the egress guard (round 32, architecture and security, *high*): a Geminarr that runs an attacker's code can still ask the browser, over the debugging port, to send what it holds anywhere that the browser may reach.
- **Where**: ADR 0020 ("what it does not cover"), `docs/network.md`, `SECURITY.md`, SPEC D-08 and §11.
- **Reason**: inherent to a Geminarr that drives a browser (ADR 0016), and measured, not assumed. Whoever holds the debugging port holds the browser's reach: a filter inside Chromium (a fixed proxy with a bypass list, an enterprise policy that blocks every address but a list) stops a page, but a context that a driver creates with a proxy of its own sends a request from an allowed page to any host, so a route filter in the product would be a filter that the same attacker removes. What bounds it is the pod's network policy **by name** (advised in `network.md`), the dedicated account, and the fact that the same attacker already holds the session through that port. The egress guard (R-24-2) stops everything that Geminarr can do by itself. This is the maintainer's to accept or to refuse: it is the price of the design.
- **Approved**: _awaiting the maintainer_
