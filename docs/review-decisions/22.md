# Review decisions of pull request #22

The answers to the findings of the four review agents on the head commit `2ca3e40`, and to SonarQube. See the [README](README.md).

## R-22-1 | quality | major | fixed

- **Finding**: A conversation that keeps growing at the same rank of the list is never opened again (new turns do not move a conversation that already heads the list), so its turns are not sent.
- **Where**: src/Geminarr.Core/Pipeline/PassRunner.cs, `Candidates`
- **Reason**: Real. The most recent conversation is looked at at every pass; the rule is in the spec, the ADR and a test.

## R-22-2 | architecture | major | fixed

- **Finding**: Mnemarr's positions are cached for an hour and nothing resets them when the destination changes (unlink, a new address, another machine name).
- **Where**: PassRunner, LinkService
- **Reason**: The link has a generation that changes with every destination change; the pass asks for the positions again when it changed. A test.

## R-22-3 | security | medium | fixed

- **Finding**: A key that a pairing gave can be sent to another address when the settings change the address (`EnsureAddress` also overwrote the row).
- **Where**: LinkService, DestinationStore
- **Reason**: A key belongs to the Mnemarr that gave it (the address of the row is kept); it is never resolved for another address, with tests for both ways. A key the deployment gave as a file stays the deployment's to bind.

## R-22-4 | security | medium | fixed

- **Finding**: Unlink answers 204 and keeps sending when the key is a file on a read-only mount.
- **Where**: LinkService.Unlink, MnemarrController
- **Reason**: Unlink says so (409, "take it out of the manifest") when the key is still there.

## R-22-5 | quality | medium | fixed

- **Finding**: An exception that is not one of the three that a pass catches (a value in the database that cannot be read) escapes and kills the scheduler's loop.
- **Where**: PassRunner
- **Reason**: The run ends `failed` with the reason `internal-error`, the error is logged, the application stays up; a test.

## R-22-6 | security | low | fixed

- **Finding**: A pairing check in flight can bring a key back after an unlink; answers of Mnemarr have no size limit; the whole outbox is decompressed in memory at each pass; unlinking leaves text of conversations in the outbox; the approval link may point to any http address.
- **Where**: LinkService, MnemarrClient, OutboxStore, PassRunner
- **Reason**: The key is kept only if the pairing is still the one that waits, and one question is asked at a time; an answer is read up to 16 MiB counting what arrives; the outbox is read by pages of 20 batches; unlinking clears the outbox; a plain-http approval page is not shown when Mnemarr is https. Tests for each.

## R-22-7 | architecture | minor | fixed

- **Finding**: A pairing completes only while the page is open; the attention link refuses an address with a path; the checks of Mnemarr and of the connection blame the pairing and the sign-in when the database is down; the source of the lines is fixed to `web`; a heartbeat is tried when Mnemarr could not be reached; two rows of the same file in DEPLOYMENT and examples that do not show the key.
- **Where**: PassScheduler, MnemarrAddress, health checks, IConversationReader, DEPLOYMENT.md, deploy/
- **Reason**: The server asks about a pairing too, every three seconds; the attention link keeps a sub-path; the two checks say `database-unreadable`; the reader says its source; no heartbeat when Mnemarr is unreachable or refuses; the rows are merged and the examples show the key file.
