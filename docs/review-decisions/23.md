# Review decisions of pull request #23

The answers to the findings of the four review agents on the first head commit `b559419`, and to SonarQube. See the [README](README.md). The head was then rebased on the pull request below it (#22), which changed the pass, the tracker and the heartbeat.

## R-23-1 | security | high | declined

- **Finding**: Chromium runs without its own sandbox (Playwright's default makes it start with `--no-sandbox`) and nothing says so.
- **Where**: PlaywrightBrowserHost, ADR 0015, SECURITY.md
- **Reason**: The sandbox needs user namespaces or a relaxed seccomp profile that a hardened container does not give: Chromium would not start. It is now stated (ADR 0015 §8, SECURITY.md, `docs/configuration.md`) with what holds instead, and `GEMINARR__BROWSER__CHROMIUMSANDBOX=true` turns it on where the platform allows it. The default stays off. **For the maintainer to accept or to refuse: it is the browser's privilege model.**

## R-23-2 | security | medium | fixed

- **Finding**: The default allowed hosts include domains that serve what anybody uploads (`storage.googleapis.com`, `googleusercontent.com`), and every kind of request is allowed to them, navigations included.
- **Where**: OriginPolicy, BrowserOptions
- **Reason**: A page is navigated to only if it is the assistant's (or a sign-in page in a live view); the hosts of files serve subresources only; the defaults name the hosts (`lh3` to `lh6` pictures, `fonts.googleapis.com`, `www.googleapis.com`) instead of whole domains. Tests of the policy; the real Gemini page is to be walked against the list by the spike S1.

## R-23-3 | security | medium | fixed

- **Finding**: The route filter does not cover WebSockets, and Chromium's own background traffic never goes through a route.
- **Where**: BrowserSession, docs/network.md
- **Reason**: WebSockets go through the same policy (`RouteWebSocketAsync`, `wss` read as `https`); `docs/network.md` says that the background traffic is held by `--disable-background-networking` and the network policy, not by the filter.

## R-23-4 | security | low | fixed

- **Finding**: `LogError(ex, …)` and `LogWarning(ex, …)` write the message of a browser's error, which holds its command line and addresses.
- **Where**: PlaywrightBrowserHost, BrowserSession, LiveViewSocket
- **Reason**: Only the kind of error or of failure is logged.

## R-23-5 | security | low | fixed

- **Finding**: The operator's session is checked only when the WebSocket opens: after a sign-out the live view goes on.
- **Where**: LiveViewSocket, AuthController
- **Reason**: Signing out closes the live view (one operator: a view belongs to the session that is signed in).

## R-23-6 | security | low | fixed

- **Finding**: `SignInEnded(true)` runs a second time in the `finally`, after a disconnect, and writes the marker back.
- **Where**: LiveViewSocket
- **Reason**: A sign-in is settled once, where it is made; the `finally` only settles a live view that ended without one.

## R-23-7 | security | low | declined

- **Finding**: The Chromium binary is downloaded at build time with no pinned checksum and the final image is Ubuntu with a shell.
- **Where**: Dockerfile
- **Reason**: The choice of Ubuntu is ADR 0015 §7; how the binary is verified and upgraded is written with the first release (vertical 6, `docs/releasing.md`). The browser binary is the maintainer's by role.

## R-23-8 | quality | major | fixed

- **Finding**: The origin check compares the scheme too: behind the proxy that ends TLS the server sees http while the page is on https, and every live view would be refused.
- **Where**: LiveViewSocket.SameOrigin
- **Reason**: The host and the port only; integration tests: the same host on another port is refused, an `https` page behind a proxy is accepted.

## R-23-9 | quality | major | fixed

- **Finding**: If the live view fails to start after the browser was launched, the browser is never closed and holds the profile.
- **Where**: PlaywrightBrowserHost.OpenLiveViewAsync
- **Reason**: The session is disposed before the browser is released.

## R-23-10 | quality | major | fixed

- **Finding**: If the WebSocket handshake fails, the lease stays held until it expires and a new live view is refused.
- **Where**: LiveViewSocket.OpenAsync
- **Reason**: The handshake is inside the `try`; the lease is released whatever happens.

## R-23-11 | quality | major | fixed

- **Finding**: Ctrl+Alt+Escape gives the keyboard back after the keys went down in the remote browser: Ctrl and Alt stay held there.
- **Where**: frontend/src/Connection/LiveView.tsx
- **Reason**: The keys that are down are let go when the keyboard leaves (the combination, or the loss of focus); tests.

## R-23-12 | quality | minor | fixed

- **Finding**: The sign-in is settled twice; `Current()` then sees `Connecting` with no view.
- **Where**: LiveViewSocket
- **Reason**: See the answer to the security finding on the same point.

## R-23-13 | quality | minor | fixed

- **Finding**: `Resumed` returns to `connected` whenever a pass ever worked; a pause begun while `needs-login` resumes as connected.
- **Where**: ConnectionTracker
- **Reason**: See the architecture major on the state that is lost: the record keeps what it was and goes back to it.

## R-23-14 | quality | minor | fixed

- **Finding**: The wait of the session check ignores the cancellation; the check decides `reader-broken` by reading the text of an error.
- **Where**: BrowserSession
- **Reason**: The wait ends with the cancellation; the route handler records a refused navigation in a flag (volatile, as the sign-in redirect), and the text of an error is no longer read. The launch itself takes no token (it is short and bounded by the browser).

## R-23-15 | quality | minor | fixed

- **Finding**: The three tasks of the socket are not awaited after the cancel and the socket is disposed under them.
- **Where**: LiveViewSocket.RunAsync
- **Reason**: They are awaited, and the socket is disposed after.

## R-23-16 | quality | minor | fixed

- **Finding**: The state machine reaches the controller with the message of any `InvalidOperationException`; the mouse button given as a number or null is taken as left; `DisposeAsync` awaits nothing; a button released outside the screen leaves the remote mouse down; the done button does not look at the socket.
- **Where**: ConnectionController, LiveInput, PlaywrightBrowserHost, LiveView.tsx
- **Reason**: A refusal of the service has its own exception and only that one is said; a button that is given and is not a known name is refused; `DisposeAsync` returns a completed task; the pointer is captured; the done button uses the guarded send.

## R-23-17 | quality | minor | declined

- **Finding**: `Current()` writes without a lock; the policy is parsed at every request; frames may draw out of order; the tracker depends on the live view and the browser; the rules of the live view are in the host.
- **Where**: ConnectionTracker, OriginPolicy, LiveView.tsx, LiveViewSocket
- **Reason**: One operator and moves that are idempotent; the policy is a few string splits per request, measured in microseconds; a frame that arrives late is one picture; the dependencies are the ones of the state's own rules (ADR 0015 §5); moving the session loop into Core is for the vertical that gives the live view its second user.

## R-23-18 | test | medium | fixed

- **Finding**: The Browser project is left out of coverage on the claim that every decision is in Core; the rules about the profile folder are tested nowhere.
- **Where**: ci.yml, PlaywrightBrowserHost
- **Reason**: Tests on a real folder (private or not, signed-in marker, tightening, emptying without removing the folder); the comment of the CI says exactly what is and is not covered.

## R-23-19 | test | minor | fixed

- **Reason**: All added.

## R-23-20 | test | minor | declined

- **Finding**: A real 3-second wait to prove that the address alone decides, the polling helpers, the validators tested by reflection, the e2e stack runs the `Page` detection and not the default, one pixel read on the canvas, the bounds of a socket message.
- **Where**: ConnectionApiFixture, OriginPolicyFixture, tests/e2e
- **Reason**: Answered in R-22-50 and R-22-62 where they repeat; the default `Confirm` and the bounds of an input are covered at the service and parser levels, and the first real run on the dedicated account (spike S1) is where the default is walked in a real browser.

## R-23-21 | architecture | major | fixed

- **Finding**: A live view that ends without a sign-in turns a healthy session into `needs-login`, and Mnemarr sends the mail for a session that never expired.
- **Where**: ConnectionTracker, Schema step 2
- **Reason**: The record keeps the state it took over (`before_state`, `before_reason`, `before_failures`) and goes back to it; a test: connected, a live view, closed, still connected.

## R-23-22 | architecture | major | fixed

- **Finding**: Pause and resume lose the state: `needs-login` becomes connected, a degraded state becomes connected.
- **Where**: ConnectionTracker
- **Reason**: Same record, same return; a test: `needs-login`, paused, resumed, `needs-login` with its count.

## R-23-23 | architecture | major | fixed

- **Finding**: The temporary folder of the Kubernetes example (64 Mi) is too small for the browser, which keeps its shared memory there.
- **Where**: deploy/kubernetes/geminarr.example.yaml
- **Reason**: 384 Mi, within the 512 Mi of the container's ephemeral storage.

- **Finding**: The compose example keeps 256M and a `/tmp` with no size, and Chromium would be killed.
- **Where**: deploy/docker-compose.example.yml

## R-23-26 | architecture | minor | fixed
