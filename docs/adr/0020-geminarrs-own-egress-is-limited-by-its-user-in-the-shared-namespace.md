# 0020 — Geminarr's own egress is limited by its user, in the namespace that it shares with the browser

- **Status**: decided on 2026-11-17, after the review's finding R-24-2 (and its repeats) and the maintainer's refusal to accept it: "fix it"; it ends the cost that ADR 0016 accepted **for the path that Geminarr takes by itself**, and says what it leaves
- **Amended by**: [0021](0021-geminarr-has-no-debugging-port-to-the-browser.md): Geminarr has no debugging port to the browser any more, so whatever this record says of `CDPURL`, the debugging address, attaching to the browser or driving it no longer holds; the rest stands.
- **Date**: 2026-11-17
- **Spec**: D-28

## Context

ADR 0016 shares one network namespace between Geminarr and the browser container, so that the browser's debugging port (the key to the session) is on a loopback and never on a network. The price: a network policy applies to a pod, not to a container, so the egress that the browser needs (https to the assistant and to the account provider, whose addresses are not stable) also applied to Geminarr's own process, which needs only Mnemarr. A flaw in Geminarr (it parses the text of conversations, which is hostile input) could then make it connect to any host that the browser may reach. ADR 0016 wrote this as a cost that "the maintainer accepts or refuses"; the review kept it open at _major_ in five entries, and it is refused.

## Decision

1. **In the shared namespace, Geminarr's own process is named by its user and limited, whatever the pod's network policy says.** Rules of the namespace's output chain match the _owner_ of the socket (the user of the image, uid `1654`): it may answer what comes in on its two ports, reach the browser's debugging address and desktop on the loopback (those two ports, no other port of the loopback), ask the name servers that are listed, and open a connection to **Mnemarr's address and port** that are listed. Everything else is refused at once (a reset, not a silence). The browser's own processes are not named, and keep what the policy allows.
2. **The rules are set by a container of their own, once, and Geminarr cannot change them.** One-shot containers (IPv4, IPv6) share the namespace, run with the one capability that they need (`NET_ADMIN`, nothing else, a read-only file system) and exit; Geminarr starts after them and has no capability. Compose: two services; Kubernetes: two init containers. The image is the Kubernetes project's `distroless-iptables`, pinned by digest, never a tag: a third party's image, with no shell, which is why the rules are a file (a ConfigMap) and not a script.
3. **Geminarr checks that the guard is there, and fails closed.** A guard that is missing fails open and nothing else would say so (a restart that makes a new namespace, an init container left out of a folder, a user that the rules do not name, a typo). Geminarr therefore tries, at start and every few seconds, a connection to an address that is on no list (`192.0.2.1`, reserved for documentation, never routed): behind the guard it is refused at once; otherwise the desktop is closed and nothing is read, as for a port that listens off the loopback, with a reason code of its own (`egress-unguarded`). The probe tries both families (`192.0.2.1` and `2001:db8::1`) and counts a refusal at once as the guard: it measures the property that matters (an address on no list is refused to Geminarr's process), not the way that it is done; where a family has no route at all (the system says so itself, before anything is sent), its guard has nothing to say, and what a router answers on the way is not a refusal. `GEMINARR__BROWSER__REQUIREEGRESSGUARD=false` says that something else holds the rules (a warning at every start).
4. **The rules are declarative and in the repository's examples** (`deploy/egress/`), with the address of Mnemarr as a value that the operator writes: a change of that address is a change of the file and a restart, which the runbook says. The examples and the end-to-end stack hold the same image; the Kubernetes ConfigMap and the Compose file hold the same rules; a rule file that names no user or does not refuse the rest is a test failure.
5. **The end-to-end test shows it on a real namespace**: two probes in the namespace, one as Geminarr's user and one as the browser's, try the same connection; the browser's opens and Geminarr's does not, while Geminarr still reaches the browser's debugging address on the loopback and no other port of it.

## What it does not cover

**Whoever holds the debugging port holds the browser, and with it the browser's reach.** The debugging protocol can open any address in the browser, run a request from a page, create a context with its own proxy, and read the cookies. A Geminarr that is compromised **to the point of running code of its own** can ask the browser (a loopback connection that the guard allows, because Geminarr needs it) to send what it holds anywhere that the browser may reach. This was measured: a filter inside Chromium (a fixed proxy with a bypass list, or an enterprise policy that blocks every address but a list) stops a page from going elsewhere, but a context that a driver creates with a proxy of its own sends a request from an allowed page to any host. So the guard stops what a compromised Geminarr could do **by itself** (a socket of its own: a request forged on a hostile address, a flaw that makes it connect out, an exfiltration by the network) and not what it could do **through the browser**.

What bounds the second path is the browser's own reach: the pod's network policy **by name** where the network plugin filters by name (Cilium `toFQDNs`: advised, in `docs/network.md`), the dedicated account (whose damage is bounded), and the fact that the same attacker already holds the session through the debugging port. It is the price of a Geminarr that drives a browser (ADR 0016) and it is not reduced by the guard. It is written as a decision of the maintainer: R-24-34.

## Alternatives considered

- **Accept the cost (ADR 0016's)**: refused by the maintainer.
- **Two pods, the debugging port on a network behind an authenticating proxy**: splits the policies, but puts the key to the session on a network and adds a component to secure and to keep up. A proxy that filters the debugging protocol cannot keep what Playwright needs. Kept as the shape for a platform that cannot run the guard.
- **A network policy that filters by name (Cilium `toFQDNs`)**: narrows the browser's reach to a list of names and so bounds the second path; it does not separate the two containers. Advised, not required (a platform may not have it).
- **A filter inside Chromium (a policy, a fixed proxy with a bypass list)**: measured, and bypassable by a driver (above). Not built.
- **A filter inside Geminarr's own code**: a process that is compromised does not obey its own filter.

## Consequences

- A platform must let the guard's container have `NET_ADMIN` (Pod Security `privileged` for the namespace, or an exemption for that container); where it cannot, the same rules belong to the node's or the network plugin's policy, `REQUIREEGRESSGUARD` is false, and this record says what they must say.
- Mnemarr's address is in the rules: a Mnemarr that moves needs the rules updated and the pod restarted. Geminarr says "unreachable" for Mnemarr (the `mnemarr` check) until then; the runbook has the entry. A name that is resolved goes through the name server of the rules: give Mnemarr by address (`hostAliases`, `extra_hosts`) and delete the two name-server lines, and no name leaves at all (a name server is a way out for a few bytes at a time).
- A service-mesh proxy that redirects the pod's outbound traffic to the loopback is not reached through the guard's loopback rule (it names the two ports of the browser); the mesh must leave Geminarr's user out of its redirection.
- Chromium runs as another user and is not limited by these rules: the assistant's host list stays the network policy's (network.md), as before.
- The nf_tables rules need a kernel with `nft` and the `owner` match (every current distribution); the end-to-end test proves it on the CI's.
