# 0014 — The pass, the outbox and Mnemarr's positions

- **Status**: accepted
- **Date**: 2026-11-13
- **Spec**: D-22, F-LNK-01 to F-LNK-04, F-RDR-01, F-VIEW-01; follows Mnemarr's ADR 0018 (storage), 0027 (enrolment), 0030 (pairing) and 0041 (the format `chat-turns` and the attention signal)

## Context

Vertical 2 is the first that keeps data and talks to Mnemarr. Everything after it (the browser, the reader of Gemini, the Takeout import) feeds the same chain, so the chain is built and proved first, with a **demonstration reader** whose conversations are invented: a reader that does not exist yet must not decide how the pipeline works.

## Decision

1. **SQLite through ADO.NET, behind one interface per aggregate, a schema in numbered steps** (`PRAGMA user_version`, a step is never edited once released, a database newer than the code is refused): the same as Mnemarr's ADR 0018, copied rather than shared (two small files, no package to publish). The file is readable by its owner only, and a data folder that does not exist is not created (a volume that was not mounted must not look like a fresh one). Step 1 holds `connection`, `destination`, `conversations`, `outbox` and `runs`. **No text of a turn is ever a column of `conversations`.**
2. **One pass is the unit of work**, in this order: (1) ask Mnemarr what it holds (the first pass and about every hour) and take it as the truth; (2) check the session and list what is recent; (3) open the candidates (new, moved up, renamed, or with turns that nothing waits to send), best rank first, at most the limit (a conversation never seen here waits until Mnemarr has been asked what it holds: nothing is read with nowhere to send it); (4) queue the lines that Mnemarr lacks; (5) send what waits, in order; (6) tell Mnemarr how it went; (7) write the run. Sending and the heartbeat happen even when reading failed (a heartbeat is not tried when Mnemarr could not be reached or refused the key: it would wait as long for the same answer), the outbox is read by pages, an error that was not foreseen ends the pass as `failed` and the application stays up, and reading is bounded in time (sending is bounded by what waits, and the scheduler wakes at least every 10 minutes so the heartbeat never waits for a slow poll interval). One pass at a time: a second is refused, not queued.
3. **The outbox is the only place a turn's text is held, and only until Mnemarr acknowledges it.** Lines are stored compressed, contiguous from where Mnemarr stands; what waits for a conversation is **replaced**, not added to, each time the conversation is queued again, so that it is always one run of lines from the position Mnemarr holds. A batch that Mnemarr rejected is kept with the reason and holds back the rest of its conversation only; the others go on. A restart loses nothing.
4. **Mnemarr's positions win, and they are asked again when the destination changes.** A conversation that this database has never seen but that Mnemarr already holds goes on from where Mnemarr stands. The most recent conversation is looked at at every pass (new turns do not move it up a list it already heads). **Mnemarr's positions win.** A restored backup or a deleted machine makes Mnemarr hold fewer lines than Geminarr believes it sent: Geminarr goes back to where Mnemarr is and sends again what is missing, without anyone doing anything. A turn rewritten after it was sent is counted and shown, never sent again (the position model cannot update a line).
5. **Joining Mnemarr is a device flow or a code, and the key is a file.** By asking (pairing: Mnemarr gives a code and a page, a person approves it there and names the machine, and the page of Geminarr asks about it every few seconds), or by a one-time code in a file for a deployment as code, or by a key file that was given. The address comes from the settings when they give it and from the page otherwise. **The key is never in the database, a log, an API answer or the page**; it is written to a file only the container's user reads, by a move over the old one. **A key belongs to the Mnemarr that gave it**: it is never sent to another address, whoever changed the address. Unlinking forgets the key and the machine **and what waits in the outbox** (text of conversations must not stay with nobody to acknowledge it); a key that is a file of the deployment and cannot be removed is said, not ignored. What Mnemarr already holds stays there. A pairing that waits is also asked about by the server, every few seconds, so that it completes when a person approves it even if the page was closed. An address that is not https (or the loopback) is refused unless a sandbox switch says otherwise, redirects are not followed, every call is bounded, and a failure says which kind it is and never what was sent or where.
6. **The state of the connection is the last pass's word**, with a rule that a network error is never "not signed in": only several passes in a row that found nobody signed in turn the state to `needs-login` (`Reader:LoginFailures`, 3 by default). The heartbeat carries one sentence with no path and no content, and the attention code Mnemarr knows (`needs-login`, `reader-broken`) with the address to answer, given only if Mnemarr would keep it. The live view, pausing and disconnecting are the next vertical's.
7. **The demonstration reader is a setting for a sandbox** (`GEMINARR__READER__KIND=Demo`), not a default: it makes three invented conversations grow, and its session ends when a file is put in the data folder, so that the whole chain, the mail of Mnemarr included, can be seen without a real assistant. The overview says when it is on. With no reader (the default), a pass sends what waits and says "Not connected" to Mnemarr.
8. **The scheduler runs a pass every `Reader:PollMinutes` (a random 20 % either way), doubled for each pass that failed in a row up to `Reader:MaxBackoffMinutes`**, and "run now" is a signal it hears. The database or Mnemarr being down is logged and waited out: the container stays up and says what is wrong through its health (`database`, `connection`, `mnemarr`, `outbox`). Only the database is a check of readiness.

## Alternatives considered

- **The pipeline built with the real reader**: rejected, the reader is the unknown (spike S1); the pipeline's behavior (positions, retries, the attention episode) is the same whatever reads, and it is tested faster with a reader that says what the test wants.
- **A queue in memory**: rejected, a restart or a Mnemarr that is down for a day would lose turns that the assistant may not show again.
- **A second copy of every conversation** (to compare with): rejected (D-06); Mnemarr's positions and a hash of the last turn are enough.
- **The key in the database**: rejected, a file with a mode is easier to protect, to mount from a sealed secret and to keep out of backups in the clear.

## Consequences

- Geminarr is useful before it can read Gemini: it can be linked, it shows up in Mnemarr as a machine, and the demonstration reader lets the maintainer see conversations arrive and be found by meaning.
- Vertical 3 adds the live view and the real states of the connection around the same tracker; vertical 4 adds the web reader behind the same port and the masking before the outbox (the demonstration reader's content is invented, so nothing is masked yet).
- A new dependency, `Microsoft.Data.Sqlite` (and `Microsoft.Extensions.Http`), is the maintainer's to accept with this vertical.
